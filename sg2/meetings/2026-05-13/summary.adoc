=== 2.7 Document Review: Quality Control Section

*Humidity constraints example*

Liu Yiming had commented that a simple humidity constraint (e.g., relative humidity ≤ 100%) should be added alongside the temperature example already in the document. William noted that some operational systems permit slightly above 100% for saturated conditions (CliDE uses 103% as the cutoff).

The group agreed that the temperature example should be prefixed with "e.g." to make clear it is illustrative, not exhaustive. This satisfies Liu Yiming's comment without adding a further prescriptive list, consistent with the minimum requirements approach.

*Internal consistency checks and metadata*

A sentence in the quality control section referenced "full access to station metadata and the complete observation history" as enabling more thorough validation in a CDMS compared to real-time systems. Peter Thorne and Dwayne Scott questioned whether station metadata is actually used in QC practice beyond basic coordinates. Peter noted that the main advantage of post-processing QC over real-time QC is the availability of the full time series (enabling spike checks, streak checks, distributional checks, and record checks), rather than the depth of station metadata.

Marcellin Habimana argued the sentence should be retained as an encouragement to capture comprehensive metadata. The group agreed that this motivation, while valid, should not be embedded in the QC section, and that the paragraph's key point — the distinction between CDMS QC and real-time operational QC — should be preserved.

David updated the text during the meeting to: "where access to the observation history allows for more thorough validation than is typically possible in real-time operational systems." The reference to station metadata was removed.

*Data retention: flagged records must not be permanently deleted*

Ge Peng raised, echoing a comment from Peter Thorne at the previous meeting, that the document should contain an explicit statement that flagged records must not be permanently deleted.

William strongly supported this, citing examples from Pacific Island countries where data failing QC checks had been permanently deleted, including a case where observations recorded in Fahrenheit were treated as erroneous and lost, and the historical precedent of ozone hole measurements that appeared anomalous but turned out to be valid.

Patrick raised the practical question of where the line falls between permanent deletion and acceptable governance (soft delete, archiving, flagging). William described CliDE's approach of moving clearly invalid data to a restricted "dungeon" area of the CDMS, not included in products but preserved for audit and potential recovery. Ian and others agreed that archiving rather than permanent deletion is the correct approach; the data may always be recoverable if an error in judgment is discovered.

Denis noted this is consistent with traceability requirements in recent WMO documentation on climatological practices, which expect a full history of data values and quality flags to be retained.

Agreement was reached that:

* Original observation values must be preserved even when corrections are applied or quality control flags are raised.
* Governance processes (product generation, data exchange) determine what is included in products, not permanent deletion.

David agreed to add an explicit statement to this effect to the quality control section, linking to the provenance requirement where relevant.

=== 2.8 Observable Element Metadata Definition (Issue #18)

Patrick raised a concern that the definition of an observable element in the document includes "observation height/depth relative to the surface" as part of the element identity. For upper air observations, height varies per observation (not per element), so including it in the element definition would prevent correct representation of upper air data. Patrick drew an analogy with mobile station coordinates, which are associated with the observation rather than the station.

Patrick also raised the question of units: if unit is part of the element definition, a CDMS would require separate element records for the same parameter measured in different units (e.g., temperature in Celsius and Fahrenheit), which is impractical for services without full instrument standardisation.

David agreed with removing observation height/depth from the element definition; this information belongs in the observation record. William agreed in principle but noted the importance of capturing accumulation or averaging period somewhere; David confirmed this belongs in the observation or measurement definition, not the element definition.

Marcellin suggested making the requirements less restrictive rather than deleting items entirely, so that implementers may include additional fields. Patrick confirmed his key concern is that height/depth and unit, as currently written, would artificially multiply element records; the approach of moving them out of the element definition was agreed as the correct resolution.

Patrick confirmed he has a number of further comments and will add them to the relevant GitHub issues after the meeting for asynchronous review.
